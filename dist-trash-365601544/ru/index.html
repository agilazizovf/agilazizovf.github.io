Alfred

[АКТИВНАЯ РАЗРАБОТКА]

Автоматизация DevOps и управление серверами Linux

Управление сервером Linux часто значит переключаться между SSH, мониторингом и командами выкладки. Alfred — модульная система на Python, которую я собираю, чтобы эти процессы жили в одном управляемом интерфейсе Telegram: мониторинг, рабочие команды, Docker и выкладка, через SSH.

СделаноСохранённые подключения к серверам и проверки CPU, памяти, диска, портов, служб, процессов и журналов, плюс отчёт о доступных обновлениях пакетов. Осмотр Docker; start, stop и restart только после подтверждения. Выкладка из Git и из образа, с историей, журналом и скриптом отката. Чат на азербайджанском, английском, русском и турецком. Приватные SSH-ключи запечатываются до записи в MySQL.
В разработкеПроверки выкладки в стиле GitHub и CI, подтверждённые команды исправления, сохранённая история здоровья и другой способ читать те же проверки: почта, Slack или веб.

┌─ Инженерия ┐

Как устроены системы

Два пути, которые я держу отдельно, и три работы, где это проявилось. Внутренности работодателей сюда не входят.

Путь запроса

  1. КлиентВызов описанного эндпоинта
  2. APIAuth, валидация, контракт
  3. СервисПравила живут здесь, не в контроллере
  4. База данныхЗапрос, которого вызов реально ждёт

Путь выкладки

  1. CommitИзменение можно ревьюить
  2. CIСборка и проверки
  3. ОбразТот же артефакт локально и в релизе
  4. ХостLinux, при необходимости Nginx перед ним

01

Производительность API и запросов

Задача
API с аутентификацией для 500+ пользователей отвечали медленнее, чем нужно. Ожидание было в пути запроса, не в отсутствующей функции.
Подход
Я смотрел на это как на доступ к данным: какие запросы выполняли обработчики, что грузил Hibernate и что API мог перестать делать. Spring Security и JWT остались границей auth.
Результат
Среднее время ответа снизилось примерно на 30%. Разрез сервисов вокруг этой работы ещё и уменьшил выкладки.

02

Производительность живого backend

Задача
Запрос медленный или неверный только в проде. Локальный путь этого не показывает.
Подход
Пройти вызов от API до запроса. Убрать работу, которая запросу не нужна. Проверить изменение на работающей системе, а не только в куске кода, который выглядел нормально.
Результат
Это текущая работа. Тайминги, форму таблиц и бизнес-правила изнутри компании я не публикую.

03

Путь релиза для четырёх сервисов

Задача
Четыре сервиса означали четыре ритуала настройки. Релиз был десятиминутной процедурой, а не пайплайном.
Подход
Docker Compose, чтобы машина поднимала набор, и CI/CD, чтобы релиз был тем же артефактом, а не вторым списком шагов.
Результат
Настройка меньше часа. Выкладка около 2 минут.
